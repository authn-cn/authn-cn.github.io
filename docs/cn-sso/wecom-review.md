# 企业微信 API / SDK 企业集成评价

> 使用[统一评价方法](./methodology.md)。本页评价自建应用、第三方应用调用企业微信服务端 API、客户端能力和回调，而不把“扫码登录三步”当成整个产品。

::: tip 结论
**80 / 100（B）**。企业微信在通讯录、消息、审批、客户联系、微信客服和第三方应用授权方面有很强的企业价值，尤其适合客户运营场景。短板是服务端 API 风格偏传统、统一类型化 SDK 和调试体验不及飞书/钉钉、业务错误常由 `errcode` 表达、回调加解密和可信 IP 带来额外运维成本。
:::

## 外部 API 的真实边界

企业微信的应用 `access_token` 代表应用，而不是某个扫码用户；但它**不等于可读取全企业通讯录**。可调用的数据由应用 API 权限、应用可见范围、通讯录授权规则、可信 IP 和具体资源权限共同限制。旧文档中“token 泄露就能读全员通讯录”的绝对说法不准确，正确结论是：泄露影响范围等于该应用已获授权的范围，因此仍应最小授权并拆分应用。

三类常见接入形态：

- 企业自建应用：服务于一个企业，使用该应用的 secret 与可见范围；
- 第三方应用：企业管理员授权服务商套件，服务商按授权企业保存永久授权信息和企业 token；
- 代开发自建应用：企业授权服务商代开发，权限申请和发布流程与普通第三方应用不同。

## API、SDK 与事件

服务端能力覆盖通讯录、消息、群、审批、打卡、日程，以及企业微信最有差异化的客户联系、客户群、微信客服等业务。Web 登录组件和客户端 JS-SDK 解决前端登录与客户端能力；回调加解密官方库帮助验证和解密事件。但相较飞书/钉钉，企业微信没有形成同样统一的“完整 OpenAPI 类型 SDK + API Explorer + 事件长连接”体验，服务端通常仍需封装原始 HTTP API。

回调往往采用加密消息体。生产接入应使用官方加解密实现，验证签名和时间戳，按事件/业务主键去重，快速返回后异步处理。通讯录、客户和审批等关键数据还应定时拉取对账，不能只依赖回调。

## 登录取人流程的正确表述

扫码登录拿到 `code` 后，后端先获取应用 token，再用 `code` 获取成员身份。是否继续调用 `user/get` 或 `auth/getuserdetail` 取决于所需字段和已获权限，并非所有登录都固定“必须三步”。`user_ticket` 可用于获取本次授权用户的敏感详情；通讯录接口则受应用通讯录权限与可见范围约束。

这套流程不是标准 OIDC，但企业工程上的重点是：

- token 仅在服务端缓存并按 `expires_in` 刷新；
- 登录、通讯录同步、客户联系使用不同应用/secret，控制泄露半径；
- `(corpId, userid)` 作为企业成员复合标识；
- 外部联系人 ID、成员 ID 和开放平台 ID 不混用。

## 企业风险与建议

1. **按业务域拆应用**：登录、通讯录、消息、客户联系不要共享一个高权限 secret。
2. **权限与可信 IP 纳入变更流程**：建立应用可见范围和 API 权限基线，变更须审计。
3. **第三方应用逐租户隔离**：永久授权码、企业 token、suite 凭据和回调数据分别加密保存。
4. **统一 HTTP 适配层**：检查 HTTP 状态和 `errcode`，映射为统一错误；实现 token 缓存、限流退避、请求审计。
5. **通讯录不能假设字段齐全**：姓名、手机、邮箱等受权限和规则影响；同步程序必须接受字段缺失。
6. **客户数据单独合规评审**：客户联系、会话内容存档等能力涉及个人信息、员工告知和更严格授权，不能按普通通讯录处理。
