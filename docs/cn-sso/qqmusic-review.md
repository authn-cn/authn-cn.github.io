> 使用[统一评价方法](./methodology.md)。本页主要依据 QQ 音乐提供给车载/设备合作方的 Android SDK 文档（B 级证据）；公众无法独立访问完整当前文档，因此所有方法名和错误码都应以项目拿到的 SDK 包复核。

::: tip 结论
**59.5 / 100（C）**。QQ 音乐车载 SDK 能提供内容播放、账号绑定、查询和第三方账号登录，适合已有商务合作的 OEM 项目。短板不是“没有 OIDC”本身，而是公开文档和服务端工具不足、账号回调协议和签名算法偏定制、版本/SLA/配额依赖项目交付，企业集成的可移植性和可审计性较弱。

## 账号绑定能力的正确评价

合作方 SDK 提供绑定、解绑、查询和第三方账号登录，绑定关系保存在 QQ 音乐侧，并由 QQ 音乐服务端回调合作方验证第三方票据。这是**账号联合/换票**，不是企业员工 SSO，也不是通用 OAuth/OIDC Provider。

该模式的优势是车厂账号可以驱动音乐账号同登同退，终端不必持久保存全部绑定关系；代价是每次关键账号操作依赖合作方验证服务，双方可用性和账号状态耦合。

## 回调签名的事实修正

现有合作方文档使用自定义 MD5 拼接签名。MD5 已不适合作为新设计的密码学签名算法，但不能仅凭“MD5 存在碰撞”就断言当前协议可以直接伪造；实际风险还取决于密钥位置、规范化、时间戳校验和重放防护。企业应要求迁移到 HMAC-SHA-256 或非对称签名，并补齐算法版本和 key ID。

在迁移前至少做到：

- 强制 HTTPS，服务端重新计算并使用常量时间比较签名；
- 严格限制 `timestamp` 偏差，缓存请求摘要/nonce 拒绝重放；
- 明确字段排序、URL/JSON 编码、空值和字符集；
- 签名密钥放密钥管理系统并具备轮换、双密钥过渡和吊销流程；
- 不依赖来源 IP 白名单作为唯一认证手段。

## 企业风险与建议

1. **将非公开能力写入合同**：SDK 平台、版本、接口清单、错误码、测试环境、上线验收、维护年限和漏洞修复时限。
2. **合作方验证服务按关键基础设施建设**：多活、限流、超时、熔断、审计和故障演练；确认 QQ 音乐的缓存与重试语义。
3. **绑定状态机要可恢复**：覆盖强制绑定、冲突、重复请求、解绑时登录、账号注销、重装和多设备。
4. **票据短时效、最小用途**：给 QQ 音乐验证的票据不要复用主站会话 token，限制 audience、操作和有效期。
5. **SDK 包做供应链治理**：校验来源和哈希，生成 SBOM，检查权限与数据采集，建立灰度和回滚。
6. **播放与会员权利单独验收**：音质、缓存、版权区域、车型、会员同步、下架和结算不属于账号登录协议，必须另列验收项。

## 已修正的旧结论

- 不再把 QQ 音乐评价为“因为不是 OIDC 所以差”；车载 SDK 本来就是内容与账号合作产品。
- 不再把 MD5 碰撞直接等同于签名已可被伪造；正确结论是算法和协议设计老旧、缺少算法敏捷性，应升级并补重放治理。
- 无公开证据的 SDK 版本、SLA、回调重试和全量错误码统一标为“需项目确认”。
